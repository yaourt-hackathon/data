01Contexte et objectif

Choisir, avec peu de temps, une architecture et des modèles qui tiennent sur nos ordinateurs et répondent juste.

La mission

Nous construisons une application qui prépare les commerciaux de Givaudan aux besoins de leurs clients. Elle analyse des sources externes (réglementation, veille marché) et les données internes (clients, produits, formules). Exemple type : lorsqu'une nouvelle restriction sur un ingrédient est publiée, l'application identifie les clients concernés et aide le commercial à les contacter avec une proposition de reformulation.

Les contraintes

Mémoire
16 Go RAM
≈ 8 à 10 Go réellement disponibles pour le modèle, une fois Windows et les outils de développement ouverts.
Exécution
100 % local
Modèles servis par Ollama sur le poste. Les données clients ne quittent pas la machine.
Temps
Hackathon
Protocole court, automatisé, rejouable en une commande.

Ce que le benchmark doit trancher

  • Quel LLM pour extraire l'information des sources et rédiger pour le commercial ?
  • Quel modèle d'embeddings pour retrouver le bon passage, avec des questions en français et des sources souvent en anglais ?
  • Quelle répartition des rôles entre le LLM et le code applicatif ?
Règle de décision. Nous retiendrons le plus petit modèle qui atteint le niveau de qualité visé (≥ 80 % à la notation, aucune information inventée sur les questions sans réponse) avec une latence acceptable en démonstration (≈ 10 s par réponse).

LLM

Un prototype fonctionnel de la partie recherche + génération existe déjà (API FastAPI, Chroma, Ollama).

Pourquoi le croisement est confié au code

Comparer une concentration à un seuil, filtrer des produits par catégorie ou faire un calcul de dilution sont des opérations exactes. Les premiers tests (section 05) montrent que les petits modèles s'y trompent régulièrement (« 0,9 % > 1,2 % »). Le LLM est donc limité à ce qu'il fait bien : comprendre un texte et rédiger. Le code garantit l'exactitude des chiffres présentés au commercial.

Conséquences sur le choix des modèles

  • Extraction structurée (JSON) fiable : critère n°1 pour le LLM.
  • Fidélité aux sources : dire « non mentionné » plutôt qu'inventer une limite réglementaire.
  • Multilingue : questions en français, textes réglementaires souvent en anglais. Cela vaut pour le LLM comme pour les embeddings.
  • Taille : modèles de 8 milliards de paramètres maximum en quantification 4 bits (≈ 5 Go). Au-delà, la machine bascule sur le disque et devient inutilisable.

04Protocole

Automatisé, rejouable en une commande, centré sur les tâches réelles de l'application.

Jeu de test

12 questions métier, posées avec leurs sources dans le prompt. Les sources sont volontairement fictives (avis réglementaire en anglais, extrait de base clients, note de veille marché) : le modèle ne peut pas répondre de mémoire, on mesure donc sa capacité à lire et respecter les sources.

CatégorieQuestionsCe qui est mesuré
Extraction2Retrouver une limite, une date, une catégorie de produit
Extraction JSON1Sortie structurée exploitable par le code
Croisement2Confronter la réglementation aux produits clients
Synthèse commerciale2E-mail client, priorisation des contacts
Refus2Dire « non mentionné » au lieu d'inventer
Fidélité au contexte1Ne pas transformer un seuil d'étiquetage en limite
Calcul1Dilution d'un ingrédient dans le produit fini
Résumé multilingue1Résumer en français un texte anglais

Conditions d'exécution

  • Température 0, graine fixe (42) : résultats reproductibles
  • Fenêtre de contexte fixée à 4 096 tokens, réponse limitée à 600 tokens
  • Même prompt système pour tous les modèles
  • Premier appel de chauffe exclu des mesures
  • Un seul modèle chargé à la fois
  • Même machine (16 Go), autres applications fermées

Mesures

Automatiques
Mots-clés attendus, validité du JSON, détection du refus, langue de réponse. Latence totale, délai avant premier token, tokens par seconde, mémoire occupée (API Ollama).
Notation par IA (Claude)
Chaque réponse est notée de 0 à 2 sur 4 critères : exactitude, fidélité aux sources, complétude, utilité pour un commercial. Total sur 8 par réponse, sur 96 par modèle.

Les contrôles automatiques seuls sont trompeurs (score maximal obtenu sur une réponse entièrement fausse) : la notation par IA est la mesure de référence. Une relecture humaine par l'équipe Data est prévue pour la version finale.

Enseignements

  • Aucun des deux modèles légers n'est utilisable seul pour un outil réglementaire : trop d'erreurs factuelles sur des questions simples.
  • Croisement et calcul échouent chez les deux. Cela confirme le choix d'architecture : la comparaison avec les données clients est faite par le code.
  • La taille joue surtout sur la fidélité : le 3B invente nettement moins que le 1.5B. Le 7B devrait poursuivre cette tendance.

Pistes écartées ou optionnelles

  • Modèles de plus de 8 milliards de paramètres : écartés, ils dépassent la mémoire disponible.
  • Fine-tuning : écarté, trop long pour le format hackathon, au profit du RAG.
  • bge-m3 (embeddings multilingues) : troisième candidat si EmbeddingGemma déçoit.
  • gemma3:4b (modèle de vision) : uniquement si les sources contiennent des documents scannés ou des tableaux en image. Il les convertirait en texte avant l'indexation.

Reproduire le benchmark

ollama pull qwen2.5:1.5b ; ollama pull llama3.2:3b ; ollama pull qwen2.5:7b
ollama pull nomic-embed-text ; ollama pull embeddinggemma
python bench.py --models qwen2.5:1.5b llama3.2:3b qwen2.5:7b

Le script (Python standard, sans dépendance) produit un fichier de résultats détaillé et une feuille de réponses côte à côte pour la notation.
